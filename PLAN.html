TenderEngine — Migration Plan

What this document is

A full record of the architecture decisions made and the plan to execute them. Covers two parallel initiatives: replacing Notion with Supabase as the data layer, and replacing the Claude Code CLI subprocess with the Anthropic SDK so the system can run on Railway without any local dependencies.

Where we are now

The problem with the current setup

The cockpit runs as a local Next.js dev server. When an agent run is triggered, the server spawns claude -p as a child process — the full Claude Code CLI binary — and passes it a prompt string that tells it to read its own instruction files from the local filesystem. The CLI connects to two MCP servers (Notion and Google Drive) that are configured in the local ~/.claude config, uses those to read and write all data, and streams output back over stdout as newline-delimited JSON. The server parses that stream and pushes events to the browser over SSE.

This means:

  • Cannot be deployed. The subprocess model requires the Claude Code binary installed locally, plus MCP config pointing at Notion and Drive. Railway has neither.
  • Run state is ephemeral. Everything lives in globalThis.__teRunRegistry. A server restart wipes every in-flight and completed run.
  • Notion is both the database and the UI. There is no independent data layer. Notion's API is slow, rate-limited, and the property model is awkward to query.
  • The agent wastes turns reading its own instructions. The agent spends two tool call roundtrips fetching its own instruction files before doing any real work. That costs tokens and time on every run.

The decisions we made

1. Replace Notion with Supabase Postgres

Why Notion is being dropped: Notion was chosen as a convenient starting point because it has a visual UI for manual data entry and an API. But as a database it has real problems: the API is slow, rate-limited, the property model is verbose to query, and it creates a hard dependency on a third-party SaaS for what is fundamentally structured relational data. Supabase gives you real Postgres — fast queries, joins, indexes, row-level security — plus a dashboard for manual edits if needed.

The Tender and Client TypeScript types in lib/types.ts already define the shape cleanly. They map 1:1 to Postgres columns with almost no changes.

2. Keep Google Drive for document storage

Google Drive was considered for replacement — Supabase Storage was evaluated as an alternative. We decided to keep Drive because:

  • The clients this system serves are non-technical. They already know how to open a Google Doc, leave a comment, and make a tracked edit.
  • Draft responses are produced as Google Docs. Clients open the shared link, edit inline, and return feedback without needing any new tool or workflow.
  • Switching to Supabase Storage would mean storing drafts as Markdown or DOCX files and building or integrating a document editor — a significant scope increase with no user benefit.

The Drive integration changes from MCP (local config) to a Google service account with the googleapis npm package. The folder structure and file URLs stay identical. Nothing changes for clients.

3. Replace the Claude Code CLI subprocess with the Anthropic SDK agent loop

The spawn('claude -p ...') call in lib/runs.ts is replaced with an in-process agentic loop using @anthropic-ai/sdk. The loop:

  1. Reads the relevant .md files and builds a system prompt before the first API call — no tool turns wasted reading instructions.
  2. Calls anthropic.messages.stream() with a defined set of tools.
  3. Executes tool calls server-side (Supabase queries, Drive API calls).
  4. Sends tool results back to the API and loops until stop_reason: end_turn.
  5. Converts streaming output into the same FeedEvent shape the existing SSE endpoint emits.

The UI, SSE layer, and all route handler signatures stay unchanged. Only the internals of startRun() change.

Why the agent .md files do not need to be rewritten: The .md files are system prompts, not discovered plugins. Loaded before the first API call, they become the system parameter. The agent instructions themselves are unchanged — only the tool names referenced in them need updating to match the SDK tool names.

4. Deploy to Railway

Single Next.js service on Railway. No separate backend process. The SDK agent loop runs inside the Next.js API route handler — same process, no subprocess, no inter-process communication needed.

  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  reference         TEXT,
  name              TEXT NOT NULL,
  client_id         UUID REFERENCES clients(id),
  deadline          DATE,
  decision_date     DATE,
  status            TEXT DEFAULT 'New',
  priority          TEXT DEFAULT 'Normal',
  result            TEXT,
  submission_method TEXT,
  owner             TEXT,
  output_doc        TEXT,
  tender_docs       TEXT,
  sections_found    INT  DEFAULT 0,
  sections_mapped   INT  DEFAULT 0,
  sections_drafted  INT  DEFAULT 0,
  gaps_found        INT  DEFAULT 0,
  blockers          TEXT DEFAULT '',
  compliance_flags  TEXT DEFAULT '',
  estimated_value   TEXT DEFAULT '',
  next_action       TEXT DEFAULT '',
  agent_notes       TEXT DEFAULT '',
  created_at        TIMESTAMPTZ DEFAULT now(),
  updated_at        TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE agent_runs (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tender_id   UUID REFERENCES tenders(id),
  agent_id    TEXT NOT NULL,
  prompt      TEXT,
  started_at  TIMESTAMPTZ DEFAULT now(),
  finished_at TIMESTAMPTZ,
  state       TEXT DEFAULT 'running',
  events      JSONB DEFAULT '[]',
  exit_code   INT
);

CREATE INDEX ON tenders (status, deadline);
CREATE INDEX ON agent_runs (tender_id, started_at DESC);

SDK agent loop — how the instruction files work

The current problem

The prompt today is literally: "Read CLAUDE.md and agents/triage-agent.md. Run triage on [URL]"

The agent's first two actions are always reading its own instructions — two tool call roundtrips before any real work begins. This costs tokens and adds latency on every run.

The fix

With the SDK, the system parameter is passed directly. The server pre-loads the files before the first API call:

function buildSystemPrompt(agentId) {
  const claudeMd = fs.readFileSync(path.join(agentRoot, "CLAUDE.md"), "utf-8");
  const agentMd  = fs.readFileSync(path.join(agentRoot, "agents", agentId + "-agent.md"), "utf-8");
  return claudeMd + "\n\n---\n\n" + agentMd;
}

The user message is then just: "Run triage on https://..." — the agent starts work immediately with zero wasted turns.

Migration phases

Phase 1 — Replace Notion with Supabase

Goal: cockpit reads and writes Supabase. Agents are unchanged in this phase — they still run via subprocess and use Notion MCP. Both sources exist in parallel during this transition.

  • 1a Create Supabase project. Run schema above.
  • 1b Write one-shot migration script — pull all Notion records, map properties to Postgres columns, INSERT into clients and tenders, validate row counts.
  • 1c Replace /api/tenders/route.ts — Supabase SELECT instead of Notion query. Response shape stays the same.
  • 1d Add /api/clients/route.ts — new endpoint backed by Supabase.
  • 1e Swap @notionhq/client for @supabase/supabase-js in package.json.
  • 1f Add SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY to .env.local.
  • 1g Smoke test — confirm tenders rail loads from Supabase.

Phase 2 — Replace subprocess with SDK agent loop

Goal: agents run in-process via Anthropic SDK. No Claude Code CLI required.

  • 2a npm install @anthropic-ai/sdk googleapis
  • 2b Implement lib/tools/supabase.ts — four handlers wrapping supabase-js queries.
  • 2c Implement lib/tools/drive.ts — four handlers using googleapis with service account auth.
  • 2d Set up Google service account locally. Test drive.ts functions in isolation.
  • 2e Rewrite lib/runs.ts startRun() — remove spawn(), add buildSystemPrompt() and runAgentLoop(). Write run state to Supabase.
  • 2f Update agent .md files — replace Notion MCP tool names with db_*, Drive MCP names with drive_*.
  • 2g Test all five agents end-to-end locally (triage, drafting, polish, onboarding, debrief).
  • 2h Remove NOTION_TOKEN and CLAUDE_BIN from env.

Phase 3 — Deploy to Railway

Goal: running in production, accessible via a URL, zero local dependencies.

  • 3a Add railway.json to tenderengine-cockpit/.
  • 3b Push to GitHub. Railway deploys from connected Git repo.
  • 3c Create Railway project, connect repo, confirm Nixpacks picks up Node 20.
  • 3d Set all five env vars in Railway dashboard.
  • 3e Deploy. Smoke test: tenders load, run triage, SSE arrives in browser, Supabase row updated, Google Doc created in Drive.
  • 3f Point custom domain at Railway service.

Phase 4 — Hardening

  • Auth — Shared-secret middleware or Supabase Auth (magic link) before sharing the URL externally.
  • Run history — Surface past agent_runs per tender in the cockpit UI.
  • One active run per tender — Reject new runs if one is already running for the same tender.
  • Health check — Add /api/health returning 200. Point Railway health check at it.
  • Timeout — Verify Railway HTTP timeout is sufficient for long agent runs (check default 300s, increase to 600s if needed).
  • Cost visibility — Log token counts from SDK result events to the agent_runs row.
